Getting this backend somewhere Amna can reach

Right now this backend only exists on your machine. This guide gets it onto GitHub, then onto Render as a real, always-on service with its own database, so Amna can build and test the frontend against it without you both needing to be online at the same time. Nothing about the app gets simplified or switched off to make this work. Real login stays on.

Last updated August 6, 2026. This is temporary infrastructure for Dev only, replaced once real Azure App Service is set up, see project-context.md in the Azure folder.

01Get the code into Farhan's repo

Farhan already created the GitHub repo and is adding you to it. Your job is to turn your local, uncommitted folder into real commits, then push them there.

1Get the repo URL from Farhan

Ask him for the repo's HTTPS URL. It looks like https://github.com/<org-or-username>/<repo-name>.git. Confirm you can see the repo at that URL in your browser first, and that you've accepted the GitHub invite he sends, before doing anything below.

2Open PowerShell in the right folder

Every command below assumes you're inside D:\Anas\MMM\Backend. Check the folder before typing anything else.

Type this 
cd D:\Anas\MMM\Backend
pwd

The second line should print D:\Anas\MMM\Backend. If it doesn't, cd to the right place before continuing.

3Commit everything you have, for real this time

Type this 
git add .
git status

Read the output of git status before continuing. It should list every real source file as staged (green), and should not list .env, node_modules, or dist, those are excluded by .gitignore already. If you see .env in that list, stop and tell me before committing, that file has real passwords in it.

Type this 
git commit -m "Initial commit: NestJS backend, auth, multi-tenant RLS"

4Point this repo at Farhan's GitHub repo and push

Replace the URL below with the real one Farhan gave you.

Type this 
git remote add origin https://github.com/REPLACE/WITH-REAL-URL.git
git branch -M main
git push -u origin main

If Farhan's repo already has its own first commit (for example, a starter README), the push above will be rejected with a message like fetch first or rejected (non-fast-forward). If that happens, stop and tell me the exact message instead of guessing at a fix. The safe fix depends on what's actually in that first commit, and the wrong one can quietly discard work.

Possible wall, worth knowing about before you hit it

Since Farhan owns the repo, connecting Render to it in Step 4 below may need his say-so too. GitHub's rule: whoever installs the Render app against a private repo needs admin rights on that repo, or the org owner needs to approve it once at the org level. If Render's repo picker in Step 4 doesn't show this repo, that's why, same shape as the tenant-admin-consent wall from the Entra work. Ask Farhan to add you as an admin collaborator (not just write access) if it happens, rather than guessing at a workaround.

02Create your Render account

You're using your own personal Render account for now, which is fine as a Dev-only stopgap, the same "this is temporary, revisit later" status as your personal Entra test app.

  1. Go to render.com and sign up. Sign up with GitHub (not email/password) so it can see your repos directly. This is the same account that'll need access to Farhan's repo from Step 1.
  2. Use your work email (@convergentbt.com) if it asks, even though it's a personal account, so it's easy to hand over to a real team account later without losing history.

03Create the shared database

Your current Postgres only exists in Docker on your laptop. Render needs its own, separate one, reachable from anywhere.

  1. In the Render dashboard, click New + → PostgreSQL.
  2. Name it something like mmm-dev-shared.
  3. Region: pick whichever is closest to you and Amna both, it doesn't need to match Azure's future region.
  4. Plan: the free tier is fine to start.
  5. Click Create Database, then wait for its status to say Available.
  6. Once it's up, open its Info tab. You'll need four values off this page in the next step: Hostname, Port, Database, and the admin Username / Password Render generated for you. Keep this tab open.

04Create the web service

This is the actual NestJS app, running continuously, redeploying itself every time you push to main.

  1. Click New + → Web Service.
  2. Pick the repo from Step 1 in the list. If it isn't there, see the "possible wall" callout above.
  3. Name: mmm-backend-dev or similar.
  4. Runtime: Node.
  5. Build command: npm install && npm run build
  6. Start command: npm run start:prod
  7. Instance type: free tier is fine to start.
  8. Find Auto-Deploy in the settings (usually already on by default when you connect a repo this way) and confirm it's set to Yes, branch main. This is the whole "push and it updates itself" part, verify it rather than assume it, since it's the reason this step is being done at all.
  9. Don't click Create yet. Add the environment variables in the next step first, they're on the same screen.

Environment variables

Same idea as your local .env, entered into Render's dashboard instead of a file. Add each of these under the web service's Environment section:

KeyValue
NODE_ENVproduction
DB_HOSTthe Postgres Hostname from Step 3
DB_PORTthe Postgres Port from Step 3 (usually 5432)
DB_NAMEthe Postgres Database name from Step 3
DB_ADMIN_USERNAMEthe Postgres admin Username Render generated
DB_ADMIN_PASSWORDthe Postgres admin Password Render generated
DB_USERNAMEmmm_app
DB_PASSWORDmake up a new strong password, write it down, you'll need it again in Step 5
DB_SSLtrue, Render's Postgres requires it, same as Azure will
DB_SYNCHRONIZEfalse
DB_LOGGINGfalse, leave the verbose SQL logging off here, it's for local only
AZURE_AD_TENANT_IDsame value as your local .env
AZURE_AD_AUDIENCEsame value as your local .env
AUTH_DEV_BYPASSfalse, stays off, real login only, this is the whole point

Don't set PORT yourself. Render assigns its own and injects it automatically; the app already reads whatever's in the environment.

Click Create Web Service once all of these are in. The first deploy takes a few minutes and will very likely fail on boot. That's expected, keep reading, it's because the database is still empty.

05Run migrations against the new database

The web service can't start yet because the tables and the restricted mmm_app role don't exist on Render's database. Migrations create both, same as they did locally, just pointed somewhere else this one time.

Read only, don't type this into a file

This runs from your own machine, once, using a temporary copy of your .env pointed at Render's database instead of your local Docker one.

  1. Make a copy of your real .env file and name the copy .env.render-setup.
  2. In that copy, change DB_HOST, DB_PORT, DB_NAME, DB_ADMIN_USERNAME, DB_ADMIN_PASSWORD to the Render Postgres values from Step 3, and set DB_USERNAME/DB_PASSWORD to mmm_app and the password you invented in Step 4. Set DB_SSL=true.
Type this 
Copy-Item .env .env.backup
Copy-Item .env.render-setup .env
npm run migration:run

Watch the output: you should see each migration listed as run, ending with CreateAppRole1785900000002. That last one is the one that actually creates mmm_app on Render's database.

Type this, right after, don't skip this part 
Copy-Item .env.backup .env -Force

That last command puts your real local .env back, pointed at your own Docker Postgres again. Confirm your local server still starts normally after this before moving on.

06Verify it, the same way TC-04 was verified

  1. Back in Render, open the web service and check the Logs tab. It should now say something like MMM backend listening on http://localhost:<port> with no crash after it.
  2. Copy the public URL Render shows at the top of the service page (looks like https://mmm-backend-dev.onrender.com).
  3. In Postman, duplicate your existing TC-04 request, point it at <that URL>/auth/me instead of localhost:3000, keep your same real token. A 200 with your real name and email back means this whole chapter worked.
