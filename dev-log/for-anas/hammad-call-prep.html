What you already know, so you don't waste time re-asking it

All of this came from Hammad's own four handover documents, and has already shaped real code. Say it back to him if you want to confirm you're both on the same page, but there's nothing here to figure out live.

The real pipeline, already proven, tested more than once

  • A job enters a queue as a tiny message: {"job_id": "abc123", "dataset_reference": "<pointer to one file>"}. Not the dataset itself, just a pointer.
  • His worker fetches that one file, checks its structure, checks the real data (negative spend, bad dates, missing values), then trains a real Meridian model on real GPU compute.
  • Progress is checkable while it runs: GET /status/abc123 returns something like {"status": "running", "progress": 0.42}.
  • When done: GET /results/abc123 returns channel performance, accuracy, and budget allocation, real numbers, not placeholders.
  • Today this whole thing runs through Colab (for the free GPU) plus ngrok (a temporary public link so our queue can reach it). Hammad's own words: "a bridge for testing only, no place in the production architecture."

What's ours to build, not his, already scoped as CMP-79

  • Hammad's worker never sees the raw uploaded file, the Configure answers, or the model settings separately. It reads exactly one JSON file, already assembled.
  • Building that one JSON, from the real dataset plus everything a user picked in Configure, Optimize, Calibrate and Hyperparameterization, is explicitly our job, stated directly in his own document, not an open question.
  • That assembly step is the one real piece of backend work still ahead. It is not built yet.

Green means built and proven. Dashed grey means ours to build, not started. Amber is the one real unknown, the whole reason for today's call.

The real questions, in order

Six questions. The first one is the one that actually blocks everything else, ask it first, the rest are follow-ups off whatever he says.

Ask 1, the real blocker

Where does a job actually go, right now, today?

"When our backend has a real job ready, what's the actual address you want us to send it to, this week?"

Why: His worker runs through Colab plus ngrok, a temporary public link that changes every time he restarts it. Without a real, current, reachable address, we can build the assembly step (Ask 3 below) but have nowhere real to send its output. This is the one thing that actually stops backend work from continuing past today.

Ask 2

Is that address stable enough to build against, or only for a live demo?

"If that link changes every time you restart Colab, how do we know when it's changed? Should we treat this as throwaway for now, or is it stable enough to actually wire up?"

Why: If it's genuinely temporary, building real integration against it is wasted effort, better to fake/stub the call and wait for Azure Container Apps (already the real target, unrelated to this decision). If it's stable enough for now, we build against it directly.

Ask 3

Confirm the exact shape of the one JSON file we have to build

"We're building the file that gets pointed at by dataset_reference, containing the raw data plus column_mapping, kpi_type, and model_configuration (calibration and per-channel carryover/saturation). Is that still the exact real shape, or has anything changed since the API Contracts document?"

Why: This is the one piece of real backend work left before a job can even be attempted. Better to confirm the shape once, out loud, than build it and find out it drifted.

Ask 4

Who creates the job_id, us or him?

"The queue message includes a job_id, does our backend generate that, or does something on your side hand one back to us first?"

Why: Small but concrete, changes exactly what our assembly step has to do. If we generate it, that's one line of code. If his side issues it, there's a request/response step before the real job can even be queued.

Ask 5

Does the status/results polling need auth?

"GET /status/:id and GET /results/:id, is that endpoint open right now, or does it need a token? If it needs one, what kind?"

Why: If our backend needs to poll for a job's status to show the user real progress, it needs to know how to authenticate to his endpoint. Missing this means a working assembly step still can't check on its own job.

Ask 6

Timeline: when does this move off Colab and ngrok?

"Roughly when do you expect to move this to something permanent? Should we plan around that date, or treat it as open-ended for now?"

Why: Not urgent to answer today, but worth knowing whether "temporary" means next week or next quarter, changes how much effort is worth investing in Colab/ngrok specifically versus waiting.

After the call, bring back exactly this

  1. The real, current address/URL his worker is reachable at (Ask 1).
  2. Whether that address is worth building against now, or should be stubbed (Ask 2).
  3. Any correction to the JSON shape above, if the contract changed (Ask 3).
  4. Who generates job_id (Ask 4).
  5. What auth, if any, the status/results endpoints need (Ask 5).
