How this file works

  1. Every real, testable piece of the backend gets a case here, the same day it's built, same rule as the dev log itself.
  2. A case only gets marked Passing once Anas has personally run it and it worked, matching the same rule as the rest of the dev log, Claude checking it isn't enough.
  3. Re-run the whole list after anything that plausibly touches it: a dependency upgrade, a schema change, moving to a new machine, before showing this to anyone outside the team. There's no automated end-to-end suite yet, this file is what stands in for one.
  4. A case that starts failing gets flagged Failing immediately, not quietly fixed and reworded. The dev log's own honesty rule applies here too.

Testing with Postman Web against the real deployed backend, everything pre-wired

TC-04

Real Microsoft login

Passing
Last run: Anas, August 6, 2026 (Postman, Send)Tool: Postman

Preconditions: AUTH_DEV_BYPASS=false, .env pointed at a real Entra app registration, Postman environment's tenantId/clientId/ scope filled in to match (both the Initial Value and Current Value columns, Postman has both), the collection's own Authorization tab configured with Client Authentication set to Send client credentials in body, not Basic Auth header.

Confirmed twice, independently, August 6: Claude via curl using Anas's real token, then Anas himself in Postman, both got the identical result, his real name and email, not a fake one. That's what actually closes this out.

  1. Left sidebar → Auth → GET /auth/me, verify a real Entra token. Click it once to open it.
  2. Click the Authorization tab (the row of tabs under the URL bar: Docs, Params, Authorization, Headers, Body, Scripts, Settings). Not Headers, the header only appears automatically once a token exists, it won't be there yet.
  3. Look at the Type field near the top of that tab.
    • If it says OAuth 2.0, continue to the next step.
    • If it says Inherit auth from parent, that's fine too, but if you don't see a Get New Access Token button anywhere on this screen, click the collection name "MMM Backend · Dev" at the very top of the left sidebar instead, and do the rest of these steps on its Authorization tab, not this request's.
  4. Scroll down past the configuration fields (Grant Type, Auth URL, Access Token URL, Client ID, Scope, ...), these are already filled in from the environment, leave every one of them alone. Keep scrolling until you find a button labeled Get New Access Token. Click it.
  5. A new window opens showing a real Microsoft sign-in page. Sign in with your own Convergent Business Technologies account, the same one registered in Entra ID. If it asks you to approve permissions, click Accept.
  6. That window closes on its own and Postman shows a token confirmation screen with a green Use Token button. Click it. (If nothing appeared and the window just closed, the sign-in didn't complete, go back to step 4 and try again.)
  7. You're back on the request now. The Authorization tab should show a token listed under "Current Token" or similar, proof one is actually attached.
  8. Double-check before sending: click the Headers tab. You should now see one more header than before, Authorization: Bearer eyJ.... If it's not there, the token didn't attach, go back to step 4 and redo it, don't click Send yet.
  9. Click Send.
Expected result

200 OK, your real oid, email, and name, devBypass: false. Not dev-bypass-oid.

If you get 401 "Missing or malformed Authorization header"

This means no token was ever attached, the same thing that happened the first time this was tried. It's not a code problem, it means step 4 to 6 above didn't actually complete. Redo them slowly, and check the Headers tab (step 8) before clicking Send, not after.

TC-13

Upload validation: wrong or fake files are rejected

Passing
Last run: Claude, August 12, 2026, a real Jest suite plus a direct script against the real sample datasetTool: src/modules/datasets/validators/validate-dataset-file.spec.ts (9 real cases, all passing), and Postman for the hands-on version below

Until now, the upload endpoint accepted any file at all, any extension, any bytes, straight into R2. That's fixed: every upload is checked before it's ever stored. Extension has to be .csv, .xlsx or .parquet (matching what the real screen says), and the file's actual bytes have to match that extension, not just its name. A CSV has to decode as real text with a header row and at least one data row. An XLSX has to start with a real zip signature. A Parquet file has to carry its real PAR1 magic bytes at both ends. Renaming malware.exe to malware.csv does not get past this.

To try it yourself in Postman:

  1. Open Datasets (CMP-38) → POST /projects/:projectId/datasets, upload a real file (same request as TC-12).
