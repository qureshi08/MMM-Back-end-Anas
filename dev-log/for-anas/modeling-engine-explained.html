01Why this can't be one API call

A two-sentence reminder, not a re-teach, this part you already have in ARCHITECTURE.html.

A real model can take minutes to hours to train. So the backend never trains anything itself, it hands the job to a separate worker and moves on. Everything below is what that worker, Hammad's part, actually is.

02The three real pieces, tracing one real job

Not a description of the code, a trace: a real job, job_id "abc123", followed from the moment it's sent to the moment its results are ready. Every box below is a real file Hammad wrote, doing exactly the one thing it says.

Three real files run this whole trace: api.py (the three endpoints), celery_app.py + tasks.py (the queue and worker), and job_processor.py (ties every modeling step together in order).

03The one job that's still yours

The single most important thing in this whole handover. Hammad's own document says it directly: the pre-assembly step, joining the raw dataset, the column mapping, and the model configuration into one file, "is not this scope's responsibility." It's ours.

Hammad's code never touches the raw file, and never queries more than one file. It reads exactly the one JSON at dataset_reference. Building that JSON is the real shape of CMP-79, which every earlier doc on this project listed as "not yet defined." It is defined now, by this handover.

04Where "model selection" came from, and the final answer

Farhan's screenshot showed Cassandra letting a user pick between Sibyl, Robyn, and Meridian. Real, for Cassandra. Not real for us, not yet, but the dropdown stays anyway.

There's only one real engine, already built

Hammad's handover is explicit: "Given a marketing dataset, it trains a real model through Google's Meridian." One engine, already proven on real GPU training, more than once. Farhan's request almost certainly came from looking at Cassandra, a tool that genuinely supports several engines, without knowing ours only has one today.

The final, confirmed answer: keep the dropdown. One real option in it today (meridian), but the field itself is real and caller-supplied, same structure and flow as Cassandra's, built to scale to more models later without a redesign. Today's dataset upload screen and API both carry a real modelType choice, it just currently has one correct answer.

What Cassandra's screens actually are, though, is still useful, just not as a model picker. Its wizard steps line up almost field-for-field with what Hammad's real contract needs:

05Colab was never the destination

Answering your direct question: yes, this was already the plan, this handover doesn't change it.

Colab has a GPU, the local machine testing this doesn't, so training is bridged over to it through a temporary public URL (ngrok) for testing and demo purposes only. Nothing about that changes what the real deployed system looks like.

06What's proven, and what's still a known gap

Straight from Hammad's own overview, not softened, not guessed at.

Fully proven, tested multiple times

  • The full pipeline: fetch, structural check, real data validation, warnings, configuration, training, results extraction, budget allocation, packaging
  • The queue and worker system, jobs sent, picked up, processed, checked independently after
  • Multiple jobs queuing correctly, successes and failures both handled cleanly
  • Real Meridian training on real GPU compute, real sane results, not placeholder data
  • The full local-plus-Colab setup, run end to end more than once

Built and working, with known open gaps

  • Results are written to Redis as a stand-in, not a real database yet. The schema decision exists, the write doesn't
  • saturation_curves' effect field isn't yet confirmed to be a clean percentage
  • Budget allocation's structured-data extraction leans on a less-documented Meridian method, flagged directly in the code's own comments

07What's next

Read the four documents, in this order: Handover_Overview_v2.docx first (the big picture, already summarized above), then Codebase_Reference_v2.docx (every file, what it does), then Execution_Guide_v2.docx (how to actually run it), then MMM API Contracts - v6 Draft.docx (the exact shapes above, in full). Results_Field_Glossary_v2.docx is a reference for later, once results actually need displaying.

CMP-79 is answerable now. It was tracked as "define the job queue message contract," and that contract already exists, in the API Contracts document. The real remaining work is the assembly step in Section 03 above: taking an uploaded dataset plus a column-mapping step plus a configuration step, producing the one JSON file, saving it to Blob (Cloudflare R2 for now), and sending the small pointer message to the queue.

The Dataset schema is settled, final answer. modelType is a real, caller-supplied dropdown, one value today (meridian), built to scale, same structure as Cassandra's own picker. See Section 04's confirmed answer above.

The tunnel is: Sign in → Projects → Upload Data → Configure. Upload Data is one screen carrying both the model dropdown and the file, matching Cassandra's own combined screen exactly. Configure comes after, column mapping only, a separate step from the model choice.

Confirmed with Farhan already: the dropdown stays, one real option today, built to scale. Nothing further to resolve on this point.
