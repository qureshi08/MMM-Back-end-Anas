AUGUST 3, 2026

Backend scaffolded from nothing
  • Chose TypeORM over Prisma or Drizzle. The schema needs one open database connection per request to enforce which company can see which rows, and TypeORM is built for that; the other two aren't.
  • Built the project structure: database connection, the tenants and users tables, the migration that creates them, and the Auth module (token checking, a dev-only bypass so work can continue before a real login exists).
  • Built /health and /auth/me, the first two working endpoints.
  • Everything checked before Docker even existed on this machine: the code compiles, the tests pass, and the app correctly refused to start without a real database instead of silently pretending one was there.

AUGUST 5, 2026

CMP-42 built: real tenant isolation, not just a plan for it
  • A real login now creates a tenant and a user automatically, the first time it happens, matching the open-signup decision from August 4.
  • Postgres itself, not just application code, now refuses to return another tenant's rows. Proved it with real queries before trusting it, and a good thing too:
  • Found a real gap along the way. The database user the app had been using since day one turned out to be Postgres's own bootstrap superuser, which bypasses this kind of protection no matter what's configured, and Postgres refuses to ever change that. Fixed by giving the app a second, separate, deliberately weaker login of its own, migrations still use the original one. Re-tested with real queries afterward to confirm it actually works now, not just that it looks right on paper.
  • Verified the whole thing end to end: the same login called twice creates nothing twice, the actual database rows match what came back over the API, and the existing test suite still passes.

  • Anas realized he didn't need to wait on Farhan at all: the scope allows individual sign-in consent, no admin role required, just an admin role to pre-approve it for everyone at once. Registered his own dev/testing app, found and fixed two more real Entra snags along the way (a redirect URI conflict, an unverified-publisher block from the app's account-type setting), and wired .env to it himself. AUTH_DEV_BYPASS is off. /auth/me now correctly returns 401 with no token. One Postman click away from his own first real sign-in.
AUGUST 6, 2026

Real Microsoft login actually works
  • First real attempt surfaced a real chain of problems, one after another, not one bug: a Postman request pointed at a blank auth config instead of the working collection-level one, a leftover placeholder tenant ID that had never actually been overwritten, closing the sign-in window too early (Claude's own bad advice, corrected), a client-authentication setting mismatched for a no-secret app, and finally a real Entra quirk, the token's own audience field didn't come back in the format we'd assumed.

  • Fixed the audience check in the code itself, not just the config: Entra doesn't consistently issue the full API address as the token's audience, sometimes just the bare ID. The guard now accepts either form. Updated the two unit tests that check this.
  • Verified with Anas's real token, called /auth/me myself: his real name, email, and object id came back correctly, devBypass: false, and a proper tenant and user got created for his real login.
  • Added a short, honest addendum to lesson 04 about the audience quirk, not a whole new lesson, this doesn't introduce a new concept, it's a real-world footnote on one already taught there.
  • Anas then clicked Send himself in Postman and got the identical result, real name, real email, devBypass: false. Two independent confirmations, same answer. TC-04 is Passing, and the Auth module is genuinely done, both modes, not just claimed.
AUGUST 6, 2026

Projects CRUD built (CMP-41), plus a real bug found before Anas ever saw it
  • Built the full projects table and all five routes: create, list, view, edit, delete. Only the owner can edit or delete their own project, verified with a real second user, not assumed from reading the code.
  • Real bug found and fixed before any handoff: a partial update sending only one field (say, just a new name) was silently wiping every other field, including description, down to null. Traced to how the validation library builds the update object, not a typo, confirmed with a small throwaway script before touching the fix. Re-verified after: a name-only update now leaves everything else exactly as it was.
  • Verified everything against real Postgres before writing a single line of this entry: create, list, view, partial update, full update, soft delete (the row stays in the database with a deletion timestamp, it doesn't disappear), a made-up id correctly rejected, a well-formed but nonexistent id correctly 404s, and the owner-only rule blocking a second real user from editing or deleting someone else's project.
  • Anas then ran every one of TC-06 through TC-10 himself, create, list, view, the partial-update fix confirmed for real (not just by Claude), soft delete, and the owner-only rule blocking a second real user, all in Postman and pgAdmin, all Passing.
  • Mid-testing, the local database got fully wiped, tenants, users, and projects all empty. Most likely cause: pgAdmin's Query Tool runs the whole accumulated script when Execute is clicked with nothing highlighted, not just the last line typed, so an earlier DELETE in that same buffer re-ran along with everything else. Not data corruption, a clean cascade (every table has ON DELETE CASCADE), and fully recoverable: one authenticated request (GET /auth/me) auto-provisioned a fresh tenant and user, same first-login logic CMP-42 already relies on, and testing continued from there with no further issues. Worth remembering for any future pgAdmin session: highlight the one query you mean to run, don't rely on the buffer only containing what you currently see.
