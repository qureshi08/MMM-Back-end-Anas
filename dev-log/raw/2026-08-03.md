## Decisions

- **ORM: TypeORM**, not Prisma or Drizzle. Asked Anas via AskUserQuestion
  rather than picking silently, since 4 developers will share this code.
  Reason: the schema design puts `tenant_id` on every table and relies on
  Postgres Row-Level Security via a session-scoped `SET LOCAL`, which needs
  one open connection per request. TypeORM's QueryRunner pattern gives that
  directly; Prisma/Drizzle's pooled-client model fights it.
- **Fresh scaffold**, no existing repo to work from. Confirmed via
  AskUserQuestion.
- **`jose`, not passport-azure-ad or MSAL**, for Entra JWT verification.
  Smaller surface, direct control over the multi-tenant issuer check.
- TypeScript pinned `~5.9.0` (not `7.x`) — `ts-jest`'s peer range is
  `>=4.3 <7`, checked live via `npm view` rather than assumed.

## Built

- NestJS 11 + TypeORM 1.1.0 project skeleton, versions checked live via
  `npm view` rather than guessed.
- `src/config/env.validation.ts` — every env var validated at boot
  (`class-validator`), including a hard check: refuses to start if
  `AUTH_DEV_BYPASS=true` and `NODE_ENV=production` at the same time.
- `src/config/database.config.ts` — one `buildDataSourceOptions()` function,
  shared by the running app and the migration CLI, so they can never point
  at different databases.
- `src/common/entities/base.entity.ts` — `id` / `createdAt` / `updatedAt`,
  extended by every table.
- `Tenant` entity (`tenants` table) — `TenantStatus` enum
  (active/suspended/deprovisioned).
- `User` entity (`users` table) — `GlobalRole` enum, `tenantId` FK with
  cascade delete, email unique **per tenant** (not globally), soft delete
  column.
- `src/database/migrations/1785772341863-InitialSchema.ts` — hand-written
  SQL, not auto-generated, with explicit `CHECK` constraints on the enum
  columns and the unique tenant+email index.
- `EntraJwtVerifier` — JWKS-based signature verification via `jose`. When
  `AZURE_AD_TENANT_ID=common`, no single issuer string can be pinned, so it
  instead checks the issuer *shape* matches
  `https://login.microsoftonline.com/<tenant-guid>/v2.0`. 4 unit tests,
  fully mocked, no network calls, all passing.
- `EntraAuthGuard` — registered globally. Order: `@Public()` routes pass
  through, then `AUTH_DEV_BYPASS` (injects a fake dev user), then real
  Bearer token verification. Generic `UnauthorizedException` on any
  failure; real error only in a debug log.
- `GET /health` (`@Public()`) — runs `SELECT 1` against Postgres, so a
  green response proves real DB connectivity, not just process liveness.
- `GET /auth/me` — returns exactly what the guard verified from the token.
- `AllExceptionsFilter` — one consistent error shape across the API.
- `docker-compose.yml` — Postgres 16 (matches Azure Flexible Server's major
  version on purpose), healthcheck, named volume for persistence.
- `README.md`, `CONTRIBUTING.md`, Postman collection + dev environment
  (OAuth2 Authorization Code + PKCE wired at the collection level).
- `git init` in `Backend\`. No remote yet — team will create the shared repo
  later. Nothing committed.

## Deliberately NOT built

Mapping a verified Entra identity to a row in our own `tenants`/`users`
tables. `GET /auth/me` proves the token is valid; it does not decide which
platform tenant that user belongs to. That's a real open product question
(who gets auto-created on first login vs. who has to be invited, decided at
Marketplace subscription time or elsewhere) — flagged in the README and in
the `/auth/me` code, not silently invented.
