## Built

- **`tenants.external_key`** column + unique index (migration
  `1785900000000-AddTenantExternalKey`). How a login maps to a platform
  tenant: `org:<Entra tid>` for company accounts, `personal:<Entra oid>`
  for personal Microsoft accounts (every personal account shares the same
  fixed Microsoft consumers pseudo-tenant ID, so `tid` alone can't group
  them — flagged in code comments as the still-open "how should personal
  accounts group" question, same one noted in `CMP-42`'s description).
- **Real Row-Level Security on `users`** (migration
  `1785900000001-EnableUsersRls`): `ENABLE` + `FORCE ROW LEVEL SECURITY`,
  one policy checking `tenant_id = current_setting('app.tenant_id', true)`.
- **`TenantContext`** (`common/tenant/tenant-context.ts`): AsyncLocalStorage
  carrying the current request's tenant-scoped QueryRunner, chosen over
  NestJS request-scoped providers to avoid re-instantiating the whole
  provider graph per request.
- **`TenantContextInterceptor`**: runs right after `EntraAuthGuard` on every
  non-`@Public()` route. Opens one QueryRunner per request, in one
  transaction; resolves/provisions the tenant and user on it; wraps the
  route handler in that same context; commits on success, rolls back on
  error.
- **`TenantResolutionService`**: the actual first-login provisioning logic,
  implementing the 2026-08-04 open-signup decision. Find-or-create tenant
  by `externalKey`, then find-or-create the user within it. First user in a
  new tenant gets `administrator` — provisional, same "revisit before GA"
  caveat as the signup decision itself.
- Extended `AuthenticatedUser` with optional `tenantId`/`userId`, set by the
  interceptor after the guard runs. Updated `/auth/me`'s doc comment, it no
  longer says resolution is deferred, because now it isn't.

## A real architecture problem found and fixed, not assumed away

Manually proved RLS via `psql` before trusting it: with no `app.tenant_id`
set, expected 0 visible rows, got 1. With the wrong tenant id set, expected
0, got 1 again. RLS was configured correctly and doing nothing.

Root cause: `mmm_dev` (the app's only DB user until today) is the official
Postgres Docker image's bootstrap superuser. Superusers bypass RLS
unconditionally, `FORCE ROW LEVEL SECURITY` doesn't touch them. Tried the
obvious fix, `ALTER ROLE mmm_dev NOSUPERUSER` — Postgres refused outright:
"the bootstrap user must have the SUPERUSER attribute." Not demotable, by
design, ever.

**Real fix: a second, restricted role.** `mmm_dev` stays superuser, used
only for migrations (needs DDL rights: `CREATE TABLE`, `CREATE POLICY`,
...). A new role, `mmm_app`, `NOSUPERUSER`, granted exactly
`SELECT/INSERT/UPDATE/DELETE` on the schema (plus `ALTER DEFAULT
PRIVILEGES` so future tables are covered automatically) is what the running
app actually connects as now. Introduced `DB_ADMIN_USERNAME`/
`DB_ADMIN_PASSWORD` (migrations, `mmm_dev`) alongside the existing
`DB_USERNAME`/`DB_PASSWORD` (the app, now `mmm_app`). `docker-compose.yml`'s
`POSTGRES_USER` now reads from the admin pair, so the bootstrap superuser
is still created correctly. New migration `1785900000002-CreateAppRole`
creates `mmm_app` and grants it, idempotently, password sourced from
`process.env.DB_USERNAME`/`DB_PASSWORD` rather than duplicated.

Re-ran the exact same `psql` proof as the restricted role afterward: 0 rows
with no context, 1 with the correct tenant, 0 with the wrong one. That's
the real result this whole ticket needed.
