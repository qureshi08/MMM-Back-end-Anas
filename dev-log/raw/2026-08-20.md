# 2026-08-20

## Real Meridian training issues found and fixed, end to end

Multiple real training failures chased with real evidence (Colab logs, browser Network tab, direct
production DB queries via `pg` + `SET app.tenant_id`), not guessed at:

1. **Multicollinearity rejection was correct, not a bug.** Meridian's own EDA step (`vif_threshold=5`
   in Hammad's `optimize_data.py`) was correctly rejecting datasets with near-duplicate channels. The
   real gap: "combine similar channels" only fed a chart preview, never actually changed what got sent
   to training.
   - Added `apply-channel-combinations.ts` — sums `sourceColumns` into `newColumnName` per row, drops
     the originals, wired into `assemble()` before the job payload is built.
   - Added a real `POST /datasets/:id/combine-channels` endpoint (persists the combination, replacing
     the old chart-preview-only `combine-columns`).
   - Added `suggest-channel-combinations.ts` (real Pearson correlation, union-find grouping so a
     three-way correlated chain combines together) and `POST /datasets/:id/auto-combine-channels` — a
     one-click "combine what's flagged" button, Anas's own suggestion after asking "why not
     auto-suggest, it's hard for a user to configure this."
2. **Real concurrency bug**: nothing on our side or Colab's queues jobs, so two real trainings could
   run on the same GPU process and crash each other. Confirmed live — job B's "Sampling from prior..."
   started before job A's had finished. Fixed: `train()` now checks `getTrainingStatus()` first and
   refuses a second run while one is in progress.
3. Confirmed a real training run completed end to end: 98.02% accuracy, real channel
   contribution/efficiency/budget recommendation data.

## Real bug: 404 from the engine's status endpoint was silently faking progress

The engine's job registry lives only in whatever Colab process happens to be running — nothing durable
backs it. Any time that notebook restarts, every job it was tracking is gone, and future status polls
404 forever. `getTrainingStatus()` used to swallow that 404 and fall through to an elapsed-time mock
fallback, faking a progress bar for a job that was never coming back. Fixed: a 404 is now reported as
a real, permanent `FAILED` status with a clear reason, same path as an engine-reported failure. Cleaned
up 5 real orphaned rows in the production database left over from a Colab restart on 2026-08-18
(`brand compaign`, `3rd test`, two `1st test` rows, `Testing`) — marked `failed` so they stop being
silently polled forever.

## Settings page: Members, invites, notification preferences — real, not mock

Anas: "we need to make it real and functional... Need ability to invite the members, and email
sending on every action completed." Scoped and built same day (Subscription/Marketplace billing
explicitly left mocked, labeled honestly — real billing is a separate, bigger project pending

  `@InjectRepository` directly on an RLS-protected table (the pattern every other service in this repo

  `ProjectsService`/`DatasetsService`.
- Real endpoints: `GET members`, `GET members/invites`, `POST members/invite`, `PATCH
  members/:id/role`, `DELETE members/:id`, `GET`/`PATCH me/notification-preferences`.

  `NotificationService` (`sendInvite`, `sendRunCompleted`, `sendRunFailed`), wired into
  `DatasetsService` so a real completion/failure email fires once per run (`notifiedAt` guard).
- **Real security gap found and fixed**: every new sign-in used to become Administrator, not just the
  first person into a brand-new tenant — flagged as "provisional" in an old comment, never revisited.
  Now: first user of a new tenant → Administrator; anyone else → the role their pending invite
  specified, or Marketing Analyst by default.
- **Real bug found and fixed after Anas tested a live invite**: the tenant's display name was being
  set to whichever person happened to sign in first (`tenant.name = user.email`), so every invite
  email read "added you to amna.minhas@convergentbt.com's workspace." Fixed for future tenants (org
