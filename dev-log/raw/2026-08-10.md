## Real MSAL implementation, built by Amna's own Claude session

Following the real (not bypass) MSAL plan written into `TEAM-GUIDE.html`
Section 6, real problems were hit and fixed along the way, each one a
genuine finding, not user error:

1. **`AADSTS50011` redirect URI mismatch**, twice, once for
   `http://localhost:4200`, once for the real Vercel URL
   `https://mmm-frontend-amna.vercel.app`. Both needed adding as
   **Single-page application** platform redirect URIs in the Entra app
   registration (not Web, Web does not support the CORS token exchange
   MSAL.js needs). Fixed by adding both.
2. **`BrowserAuthError: timed_out`** on `loginPopup()`. The popup itself
   completed against Microsoft (a real authorization code was visible in
   its URL), but the main window's MSAL instance never received the
   result and gave up, almost certainly a Cross-Origin-Opener-Policy
   header (Vercel or framework default) blocking `window.opener` between
   the popup and the main window. Fixed by switching to `loginRedirect()`
   instead, which avoids the cross-window handoff entirely.
3. **Stale/wrong API URL**: an earlier build had `environment.prod.ts`
   pointed at a wrong or stale Render URL, found and corrected by Amna's
   Claude before the real connection could work at all.
4. **Hardcoded "Amna Minhas" header**: the welcome text and profile card
   showed a fixed name regardless of who actually signed in, a real gap
   distinct from whether login itself worked, flagged and fixed
   separately.

## A real false alarm, caused by my own verification method, not a bug

After the fixes above, testing looked convincing (a project appeared,
synced across two different people's sessions) but my own direct
database checks kept showing zero rows in `users` and `projects`, while
`tenants` correctly showed real data. Root cause: both `users` and
`projects` have Row-Level Security with `FORCE`, which applies even to
the admin database role, not just the app's restricted one. Every check
I ran was missing `SET app.tenant_id`, the one line the real application
code always sets before querying either table (see
`tenant-resolution.service.ts` and `tenant-context.ts`). Postgres was
correctly, silently hiding every row from my queries the entire time,
exactly the protection working as designed, just pointed at me instead
of an actual security threat.

Once queried correctly (`SELECT set_config('app.tenant_id', '<real
tenant>', false)` first, matching what the interceptor already does),
the real data was all there:

- 3 real users in one shared `convergentbt.com` tenant: Farhan, Anas,
  and Amna, each auto-provisioned from a real Microsoft sign-in, each
  correctly `administrator` (first-in-tenant behavior working as
  designed).
- 4 real projects, created by real people, matching what was shown in
  both Anas's and Amna's browsers exactly, cross-checked against a
  specific project id read directly out of a captured Network response
  body, not just trusted from the UI.

**Lesson worth keeping**: when a test's own verification tooling
disagrees with what real, careful UI testing shows, don't assume the UI
is lying, check whether the verification tooling itself is the thing
missing a step. Direct database checks are only ground truth if they
respect the same rules (RLS session context) the real application always
has to.
