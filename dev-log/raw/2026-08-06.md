## The chain of real bugs, in the order they were hit

1. **`TC-04`'s first guide was too thin.** Three lines assuming Postman
   OAuth familiarity. Anas hit `401 Missing or malformed Authorization
   header` and said plainly there was no real guide. Rewrote it properly,
   see yesterday's entry and `PROTOCOL.md` point 8.

2. **Request-level Authorization tab was blank.** Set to its own `OAuth 2.0`
   config instead of inheriting the collection's, so "Get New Access Token"
   tried to authenticate against empty fields. Fix: switch the request back
   to "Inherit auth from parent," fetch the token from the **collection's**
   Authorization tab instead, where the real config actually lives.

3. **"Inherit auth from parent" has no "Get New Access Token" button at
   all.** Only lets you select an already-fetched token. Confirmed by
   screenshot, not assumed. Sent to the collection's own Authorization tab
   instead.

4. **The Postman environment still had the literal placeholder text**,
   `REPLACE-WITH-YOUR-AZURE-AD-TENANT-ID-OR-COMMON`, in `tenantId`, never
   actually overwritten with the real value despite it being set weeks
   earlier. Confirmed directly from the browser's address bar during the
   failed Microsoft sign-in attempt, not guessed at. Fixed by re-entering
   the real values in **both** the Initial Value and Current Value columns,
   a Postman environment editor has two, and only one may have been filled
   in originally.

5. **Closing the sign-in browser tab manually broke the flow.** Told Anas
   he could close it once he saw "authenticated," that was wrong, Postman
   needs to detect and close it itself. Manually closing it produced
   `Error: Authentication window was closed`. Corrected: leave the window
   alone, let Postman close it.

6. **`AADSTS900144: The request body must contain client_id`.** The
   collection's OAuth2 config had "Client Authentication" set to "Send as
   Basic Auth header." Our app has no client secret (PKCE, public client),
   so Entra expects `client_id` in the request body, not tucked into a
   Basic Auth header. Fixed by switching Client Authentication to "Send
   client credentials in body."

7. **Token exchange finally succeeded** (`POST .../oauth2/v2.0/token`
   returned `200`), producing a real token: `name: "Muhammad Anas
   Quershi"`, `preferred_username: muhammad.anas.qureshi@convergentbt.com`,
   `oid: 54f32ce6-...`, `scp: access_as_user`. Genuinely his account, not a
   fluke, confirmed by reading the actual token claims, not assumed from a
   green checkmark.

8. **Our own server then rejected it anyway**, `401` from `/auth/me`
   itself, not Postman. The token's `aud` claim was
   `fa733969-d53d-46ed-81fc-119c740a5cc9`, the bare Client ID, no `api://`
   prefix. `.env`'s `AZURE_AD_AUDIENCE` had the prefix. Entra does not
   consistently issue the full Application ID URI as the audience, this
   registration produced the bare Client ID instead.

## The real fix (not a workaround)

Changed `EntraJwtVerifier` to derive **both** forms, `<id>` and
`api://<id>`, from whichever one is configured, and accept either as a
valid audience (`src/modules/auth/entra-jwt.verifier.ts`). This isn't
guessing which form to pick, it's not assuming Entra will behave the same
way for every registration going forward. Updated the two existing unit
tests to assert the array form. `.env` itself didn't need changing, the
code now handles both regardless of which one is configured there.

# CMP-41 — Projects CRUD

## What got built

`projects` table (Database Schema Design v1.1: `id`, `tenant_id`, `name`,
`description` nullable, `owner_id`, `status` active/archived, timestamps,
soft-delete `deleted_at`), migration `AddProjectsTable1785900000003`, same
shape as `EnableUsersRls`: `ENABLE`/`FORCE ROW LEVEL SECURITY` plus a
`tenant_isolation` policy. `CreateAppRole`'s `ALTER DEFAULT PRIVILEGES`
already covers the grants, nothing extra needed there.

`ProjectsModule`: entity, two DTOs (`CreateProjectDto`, `UpdateProjectDto`,
status only settable on update, never on create), `ProjectsService`,
`ProjectsController` with the five standard routes (`POST /projects`,
`GET /projects`, `GET /projects/:id`, `PATCH /projects/:id`,
`DELETE /projects/:id`, soft delete, `204`).

**Real architectural decision, not just following a template:**
`ProjectsService` does not use `@InjectRepository`, on purpose. `projects`
has Row-Level Security, and the injected default repository runs on the
app's pooled connection, which never has `app.tenant_id` set on it — a
query through it would either see nothing (fail-closed) or error. Every
query in `ProjectsService` goes through `getTenantContext().queryRunner`
instead, the same per-request tenant-scoped session
`TenantContextInterceptor` already opened, the same pattern
`TenantResolutionService` established for `users`. Worth calling out:
`UsersService`/`TenantsService` still use plain `@InjectRepository` and, as
written, would be broken against RLS-protected `users` if anything actually
called them outside of `TenantResolutionService`'s own direct
`manager.getRepository()` calls — they're currently unused dead code, not a
safe example to copy. `ProjectsService` is the real reference for how the
next RLS-scoped module should be built, not those two.

**Authorization scope, deliberately minimal:** owner-only for update/delete
right now. No administrator override, no read of `GlobalRole` at all in
this module. Sharing beyond the owner is `user_project_permissions`, its
own table in the schema doc, its own future ticket. Not built ahead of a
permission model that doesn't exist yet.

## A real bug, found before Anas ever touched it

Partial `PATCH` updates were silently wiping untouched columns. Cause:
`class-transformer` sets every declared optional DTO field as its own
property (value `undefined`) on the transformed instance, even when the
caller's JSON never included that key. `Object.assign(project, dto)` then
copied `description: undefined` onto the entity, and TypeORM's `save()`
writes an `undefined` property as SQL `NULL`. Confirmed with a small
throwaway script before touching the fix (`plainToInstance` produced
`Object.keys() = ['name', 'description', 'status']` even when only `name`
and `status` were sent). Fixed by only merging DTO keys whose value is
actually not `undefined`, in `ProjectsService.update()`. Re-verified after
the fix: a name-only `PATCH` now leaves `description` exactly as it was.

## Closed out, and a real incident along the way

Anas ran `TC-06` through `TC-10` himself in Postman and pgAdmin, all
`Passing`. Along the way he hit two real, worth-recording things, neither
of them a code bug:

1. **The Postman collection edit didn't reach his app.** Editing
   `postman/MMM-Backend.postman_collection.json` on disk changes nothing

   clean **Replace** even with no `_postman_id` in the file, better than

2. **A leading space pasted into a Path Variable's Value cell** produced

   backend bug.
3. **The local database got fully wiped mid-testing** — `tenants`,
   `users`, `projects` all empty. Root cause never fully pinned down (Anas
   couldn't reconstruct the exact sequence), but the leading theory fits
   the evidence: pgAdmin's Query Tool runs the *entire* accumulated script
   when Execute is clicked with nothing highlighted, not just the visible
   last line, so an earlier `DELETE FROM tenants WHERE ...` sitting further
   up the same buffer likely re-ran alongside everything else. Every table
   has `ON DELETE CASCADE`, so one tenant row disappearing cascades
   cleanly to zero rows everywhere, which is exactly the all-empty, nothing
   inconsistent state found. Recovery was trivial: one authenticated
   request re-triggers `TenantResolutionService`'s first-login
   provisioning, same as any brand-new environment. No code change came
   out of this, it's a pgAdmin usage habit worth remembering: highlight the
   one query you mean to run, every time, don't trust the buffer to only
   contain "the current" query.
