01The frontend, file by file

What the Angular app is actually made of, not just "the frontend talks to the backend."

02Every step of a request, in order

Not "the backend checks auth then queries the database." The real order NestJS actually runs these in, with the real code at each step, because the order is exactly why two different tenants' data can never mix even if a query forgot to filter by tenant.

1
The request arrives

The Angular app calls the backend with the real access token attached. main.ts strips the /api/v1 prefix while routing, and CORS is already open (app.enableCors()) so the Vercel origin is allowed through.

GET /api/v1/projects
Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGc...
2
The route is matched, then Guards run

Nest resolves this to ProjectsController.findAll(). Before that method can run, every Guard on the route must return true. This route has one: EntraAuthGuard. A @Public() route (like /health) skips this Guard entirely.

3
The token is checked against Microsoft, not this app's own database

EntraJwtVerifier.verify() fetches (and caches) Microsoft's real public signing keys, then checks the signature, the expiry, and who the token was issued for. It accepts either form of the audience Entra might send, because the same app registration issued the bare Client ID for this one, found the hard way on 2026-08-06.

createRemoteJWKSet(
  "https://login.microsoftonline.com/<tenant-id>/discovery/v2.0/keys"
)

jwtVerify(token, jwks, {
  audience: [bareClientId, "api://" + bareClientId],
  issuer:   pinnedIssuer   // or any real Microsoft v2 issuer, if multi-tenant
})
!
If the token fails any of those checks

The Guard throws, the request stops right here. Nothing below this line ever runs: no database connection is opened, nothing is provisioned. The caller gets 401 Unauthorized.

4
A database transaction opens for this request, and only this request

TenantContextInterceptor runs next. One QueryRunner, one transaction, scoped to this single HTTP request, not shared with any other request even on the same pooled connection.

const queryRunner = dataSource.createQueryRunner()
await queryRunner.connect()
await queryRunner.startTransaction()
5
The tenant and user are found, or created if this is a first sign-in

TenantResolutionService.resolveOrProvision() turns "a Microsoft account signed in" into "a row in this app's own tenants and users tables." A company Entra tenant maps to one platform tenant shared by everyone in it; a personal Microsoft account gets its own tenant, because every personal account shares Microsoft's one fixed pseudo-tenant id and can't be grouped by it.

externalKey = isPersonalAccount ? `personal:${oid}` : `org:${tid}`
tenant = find or create Tenant where externalKey matches

SELECT set_config('app.tenant_id', tenant.id, true)   // ← the line everything below depends on

user = find or create User where tenantId + email matches
       (first user in a brand new tenant becomes ADMINISTRATOR)
6
Every query from here on is automatically scoped to that tenant

The resolved tenantId and this same queryRunner are attached to AsyncLocalStorage, not passed as a parameter through every function call in between. Any service can call getTenantContext() and get the right one back, for this request only.

await runWithTenantContext({ tenantId, queryRunner }, () => next.handle())
7
The request body is validated

Pipes run after Guards and after the Interceptor's setup phase, right before the controller method body executes. The global ValidationPipe checks the body against the route's DTO, e.g. CreateProjectDto.

new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })
// unknown fields are stripped, a missing required field throws 400 Bad Request
8
The controller and service run, and the database enforces the rest

ProjectsController calls ProjectsService, which queries through the same QueryRunner from step 4. Postgres's own tenant_isolation policy filters every row using the app.tenant_id set in step 5, even if application code had a bug and forgot to filter by tenant itself.

9
Success: the transaction commits

queryRunner.commitTransaction(), then release(). The response is sent to the browser.

!
Failure at any point from step 4 onward: nothing is half-saved

A thrown error is caught by the global AllExceptionsFilter, which formats the JSON error body and status code, and by the Interceptor's own catch block, which calls rollbackTransaction() before releasing the connection. A first sign-in that fails halfway through provisioning never leaves an orphaned tenant with no user in it.

04The database, column by column

Every real table, every real column, exactly as the migrations created them. Not "the schema", the actual CREATE TABLE.

Postgres, deployed on Render

Multi-tenant by row, not by separate database per customer. Every tenant-owned table enforces Row-Level Security with FORCE, meaning the rule applies even to the admin database role, not just application code. Directly tested, not assumed, see Trainings/NestJS/knowledge-base/lessons/06-locked-out-by-your-own-rule.html for a real case where this caught the very people who built it.

Every arrow is a real foreign key, ON DELETE CASCADE. Delete a tenant and every user and project under it goes with it.

The exact rule that makes tenants unable to see each other's rows

ALTER TABLE "projects" ENABLE ROW LEVEL SECURITY; ALTER TABLE "projects" FORCE ROW LEVEL SECURITY; ← without FORCE, the app's own DB owner role would be exempt CREATE POLICY "tenant_isolation" ON "projects" USING ("tenant_id" = current_setting('app.tenant_id', true)::uuid);
Same policy, same wording, on both users and projects

current_setting(..., true) with missing_ok = true means a session that never called set_config matches zero rows, not an error. Fail closed, not open, on purpose.

Two database roles, on purpose

roleused bywhy
DB_ADMIN_USERNAMEthe migration CLI onlyPostgres superusers are exempt from Row-Level Security unconditionally, and the bootstrap role can never be demoted off superuser, found the hard way, 2026-08-04
DB_USERNAMEthe running app, every requesta genuinely restricted role, created by migration CreateAppRole1785900000002, granted SELECT/INSERT/UPDATE/DELETE, nothing more

05Not built yet

Real, on the roadmap, drawn dashed above on purpose

Blob Storage holds the actual uploaded dataset files, Postgres never stores the raw file, only metadata pointing at it. Job Queue and the Python Modeling Worker are how a model run actually happens, decoupled from the request that starts it, so the backend can answer immediately with a job id instead of the caller waiting minutes to hours for a response. CMP-79 defines the exact message contract between the backend and the worker before either side builds against it.

06The Azure Marketplace target

No Azure subscription exists yet, waiting on Farhan for a company-identity account, and there's no trial being pursued for shared infrastructure in the meantime. But every decision above was already made with this section in mind: nothing in the running code branches on which cloud it's talking to, only configuration does. This is the exact, named target it becomes.

Every dashed box here is the same "not built yet" meaning as everywhere else on this page, it just means "not provisioned" instead of "not coded". The code these resources would run is already written and live on Render/Vercel today.

What each one is, in real depth

from Vercel

Azure Static Web Apps

Hosts the built Angular output and serves it globally. Same build, same environment.prod.ts swap already wired via fileReplacements, moving hosts is a deploy target change, not a code change.

Free tier covers a single small app comfortably to start.

from Render

Azure App Service (Linux, Node 20)

Hosts the NestJS backend exactly as it runs on Render today. Given a Managed Identity instead of raw connection strings, so it can read secrets from Key Vault at startup without a password ever sitting in an App Service setting.

The same build command fix found on Render (installing devDependencies for the Nest build) applies here too, it's a Node/npm behavior, not a Render-specific one.

from Render Postgres

Azure Database for PostgreSQL: Flexible Server

The exact same schema, the exact same FORCE ROW LEVEL SECURITY policies, the exact same two-role split (DB_ADMIN_USERNAME for migrations, DB_USERNAME for the app). None of Section 04's SQL changes, only the connection host and credentials do.

new for target

Azure Key Vault

Where DB_PASSWORD, and any future client secret, actually lives, instead of sitting in a hosting provider's plaintext environment variable screen. App Service reads it at startup through its Managed Identity, no credential is ever typed into a dashboard by a person.

new, CMP-38

Azure Blob Storage

Holds the actual uploaded dataset files once Datasets exists. Postgres was designed from the start to store only a pointer to the file, never the file itself, so this slots in without a schema change.

new, CMP-79

Azure Service Bus

The job queue between the backend and the Python worker. The backend enqueues a message and answers the caller immediately with a job id; the worker dequeues it whenever it's free. CMP-79 is the ticket that defines the exact message shape both sides build against, before either side writes code for it.

new for target

Application Insights

Request tracing and error rates for App Service and Container Apps both, in one place. Render's own dashboard covers this today at much smaller scale; this is the real replacement once there's more than three real users to watch.

new, worker

Azure Container Apps

Runs the Python modeling worker. Chosen over a full Kubernetes cluster (AKS) because a model run is a bounded job, not a long-lived service, Container Apps scales a job's containers to zero when nothing is running and starts one per job on demand.

already live

Microsoft Entra ID, reconfigured

The exact same real service already signing Farhan, Anas, and Amna in today. For Marketplace distribution it gets reconfigured multi-tenant, so any customer's own Entra tenant, or personal Microsoft account, can sign in, not just the one Entra tenant this app registration currently trusts.

Marketplace-only

SaaS Fulfillment API webhook

The one resource on this whole page with no Dev-stage equivalent at all. A real HTTP endpoint the Azure Marketplace calls when a customer subscribes, changes plan, cancels, or renews, so the platform's own record of who's paying for what stays in sync automatically instead of a person updating it by hand. Nothing to build until there's a real Marketplace SaaS offer to receive events from. Tracked as CMP-55 and CMP-77.
