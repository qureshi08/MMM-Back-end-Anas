01Git and GitHub, the real basics

Quick reference definitions for the terms used throughout this guide. Skip ahead if these are already familiar.

Repository (repo)The whole project's folder, with its full history, living on GitHub. Ours is cbt-mmm-platform.
CommitA saved snapshot of your changes, with a message explaining what and why.
BranchYour own copy of the project's history to work on, without touching anyone else's until you're ready to combine it.
PushSending your commits from your own machine up to GitHub, where everyone else can see them.
Pull Request (PR)A request to merge your branch into another one (usually main), with a chance for someone else to look at it first.
CloneDownloading a full copy of the repo, with its history, onto your own machine, done once per machine.

For Farhan: repo owner actions

Three specific actions only the repo owner can take. Each is a separate GitHub mechanism, covered individually below.

1. Add teammates as collaborators (done, confirmed August 7)

Farhan has already invited the team; this is how everyone is able to access and push to the repository today. Kept below for reference, and for anyone added later.

  1. On GitHub, open cbt-mmm-platform, click Settings (top tabs).
  2. In the left sidebar, click Collaborators and teams.
  3. Click Add people, search by GitHub username or the email tied to their GitHub account, select them.
  4. Choose a role: Admin for anyone who needs to manage repository settings or branches, Write is sufficient for regular push and pull request work.
  5. Click Add. GitHub sends the person an invitation, which they need to accept before access takes effect.
Admin collaborator access alone will not connect Render or Vercel

This repository is under a personal GitHub account, not an organization. Third-party GitHub Apps such as Render and Vercel can only be granted access to a personal account's repositories by that account's owner. Adding someone as an Admin collaborator controls what they can do inside the repository itself; it does not let them install or authorize a GitHub App on Farhan's account. If this turns out not to match what Render's or Vercel's interface actually shows, report the exact message rather than assuming either way.

2. Connect Render and Vercel to the repository

The reliable path, given the constraint above: Farhan performs the initial connection himself, then adds teammates inside each platform's own dashboard rather than through GitHub.

  1. Sign into render.com using Continue with GitHub, with the GitHub account that owns this repository.
  2. Follow Section 4's steps to import cbt-mmm-platform and grant Render's GitHub App access to it.
  3. Once the Render service exists, invite Anas as a team member from within Render's own dashboard (Team settings), so he can manage the deployment without needing further GitHub-level approval.
  4. Repeat the same pattern for Vercel: sign in with GitHub, complete Section 5's import steps, then invite Amna as a team member inside Vercel's dashboard.

3. Create main and set it as the default branch

Hold this action until the monorepo restructuring above is agreed. Creating main from either project's current flat layout only recreates the same merge conflict on the next push.

  1. Once ready, create the branch: on GitHub, use the branch dropdown (top left of the Code tab) and type main, or run git checkout -b main locally and push it.
  2. Go to Settings → General.
  3. Under Default branch, click the switch icon, select main, click Update, and confirm.

02Your daily workflow

What to actually type, every time you sit down to work on your own branch.

First time only, on a new machine: cloning the repo

Type this 
cd D:\
git clone https://github.com/mirfarhanahmad/cbt-mmm-platform.git
cd cbt-mmm-platform
pwd

The last line should print the folder you just cloned into. Pick whatever parent folder makes sense on your machine, D:\ is just an example, matching how Anas's local backend folder is laid out today.

Then switch to your own branch:

Type this 
git checkout your-branch-name

Replace your-branch-name with the real one from the table in Section 1, e.g. frontend if you're Amna.

Every time: set your git identity once per machine

If this hasn't been done on your machine yet, git will refuse your first commit and tell you so. Set it once, matching your own name and GitHub-linked email:

Type this 
git config user.name "Your Name"
git config user.email "your-email@example.com"

This is scoped to just this one repo (no --global), on purpose, so it doesn't affect anything else on your machine unless you choose to make it global later.

Making and saving changes

Type this 
git status

Always run this before committing. It lists every file you've changed, added, or deleted. Read it, don't skip straight to committing. If you see a file you don't recognize touching, or anything named .env, stop and figure out why before continuing, that file holds real passwords and should never be committed.

Type this 
git add .
git commit -m "feat(area): what you actually changed, present tense"

The commit message format (type(area): description) is defined in Backend/CONTRIBUTING.md's Commits section, type is one of feat, fix, chore, docs, test, refactor.

Type this 
git push

The first time you push a brand new branch, git will tell you to use git push -u origin your-branch-name instead, just once, it'll say so plainly if that's what's needed.

03Opening a Pull Request

How a chunk of your work actually reaches everyone else, once main exists (see the open question in Section 1).

  1. Push your branch (Section 2 above).
  2. Go to github.com/mirfarhanahmad/cbt-mmm-platform in your browser. GitHub usually shows a yellow banner offering to open a PR for the branch you just pushed, click Compare & pull request if you see it.
  3. If you don't see the banner, click Pull requests (top tabs) → New pull request → set base to main and compare to your branch.
  4. Write a short description covering what changed and why. Commit messages already record what changed; the PR description should explain the reasoning.
  5. Click Create pull request.
  6. Ask one other teammate to look at it. Small team, keep this light, a real second pair of eyes, not a formal multi-approval process.
  7. Once they've looked, click Merge pull request.

04Deploying the backend, Render

The code is already on GitHub, committed and pushed to backend/anas (Section 1). Everything below is about getting Render itself to actually run it, continuously, somewhere everyone can reach.

Status, 2026-08-07

The first real deployment happened against a personal repository (qureshi08/MMM-Back-end-Anas), pushed to as a second remote from the same local clone, as an interim step while repo access on cbt-mmm-platform was still being resolved with Farhan. It is live and fully verified: /api/v1/health returns 200, and /api/v1/auth/me correctly enforces real login. The steps below are written against the shared repo and are what to follow once that access question is settled; they are the same steps that were actually run, just against a different remote.

Step 1Create a Render account

  1. Go to render.com, sign up with GitHub, not email/password, so Render can see the repo directly.
  2. A personal account is fine as a Dev-only stopgap, same status as the Vercel account in Section 5, migrate to a real team account before this matters beyond testing.
Known blocker, review before proceeding

The repository is under Farhan's personal GitHub account, so only he can grant Render's GitHub App access to it, being added as a collaborator does not enable this. If cbt-mmm-platform doesn't appear in Render's repo picker in Step 3 below, Farhan needs to complete the connection himself, see Section 1's "For Farhan: repo owner actions" for the exact steps.

Step 2Create the shared database

  1. In the Render dashboard, click New + → PostgreSQL.
  2. Name it something like mmm-dev-shared.
  3. Region: pick whichever is closest to the team, doesn't need to match Azure's eventual region.
  4. Plan: the free tier is fine to start, but see the note below.
  5. Click Create Database, wait for its status to say Available.
  6. Open its Info tab. You'll need four values in Step 3: Hostname, Port, Database, and the admin Username / Password Render generated. Keep this tab open.
Render's free-tier Postgres has a limited lifespan

Free-tier databases on Render are deleted after a fixed period. Confirm the exact window on Render's current pricing page at signup, since this policy has changed before and this document may not reflect the latest figure. Plan to upgrade to a paid tier, or migrate to Azure Postgres, before that expiration date, not after real team data depends on it.

Step 3Create the web service

  1. Click New + → Web Service.
  2. Pick cbt-mmm-platform from the repo list. If it isn't there, see the wall above.
  3. Branch: backend/anas for now (see Section 1's open question about main, re-point this once it exists).
  4. Name: mmm-backend-dev or similar.
  5. Runtime: Node.
  6. Build command: npm install --include=dev && npm run build. Confirmed 2026-08-07: a plain npm install here fails with nest: not found, because setting NODE_ENV=production (below) makes npm install skip devDependencies, and @nestjs/cli, which provides the build tool, lives there. --include=dev installs it anyway for this build step.
  7. Start command: npm run start:prod
  8. Instance type: free tier is fine to start.
  9. Find Auto-Deploy in the settings (usually already on when you connect a repo this way) and confirm it's set to Yes, on the branch from step 3 above. Verify this rather than assume it, it's the entire reason to deploy this way instead of by hand.
  10. Don't click Create yet, add the environment variables below first, they're on the same screen.

Environment variables

Same idea as the local .env file (Backend/.env.example shows every key with a description), entered into Render's dashboard instead of a file:

Don't set PORT yourself, Render assigns its own and injects it automatically, the app already reads whatever's in the environment.

AUTH_DEV_BYPASS cannot be true here, confirmed 2026-08-07

The app deliberately refuses to start with AUTH_DEV_BYPASS=true while NODE_ENV=production, logging This would let every request into the API unauthenticated. Refusing to start. This is intentional, not a bug, a deployed service accepting every request as authenticated with no real login is exactly what it's preventing. Since real Entra login is already fully working (Section 3, and TC-04 in the test suite), use it here instead of trying to bypass the check: keep AUTH_DEV_BYPASS=false and test with a real token, same flow as TC-04, just pointed at this service's URL.

Click Create Web Service. The first deploy takes a few minutes and will very likely fail on boot, that's expected, the database is still empty, Step 4 fixes it.

Step 4Run migrations against the new database

The web service can't start yet because the tables, and the restricted mmm_app role, don't exist on Render's database. This runs from your own machine, once, using a temporary copy of .env pointed at Render's database instead of the local Docker one.

  1. Make a copy of the real .env file, name the copy .env.render-setup.
  2. In that copy, change DB_HOST, DB_PORT, DB_NAME, DB_ADMIN_USERNAME, DB_ADMIN_PASSWORD to the Render Postgres values from Step 2, and set DB_USERNAME/DB_PASSWORD to mmm_app and the password invented in Step 3. Set DB_SSL=true.
Type this 
cd D:\Anas\MMM\Backend
Copy-Item .env .env.backup
Copy-Item .env.render-setup .env
npm run migration:run

Watch the output: each migration should be listed as run, ending with CreateAppRole1785900000002, the one that actually creates mmm_app on Render's database.

Type this right after, don't skip it 
Copy-Item .env.backup .env -Force

That restores the real local .env, pointed at the local Docker Postgres again. Confirm the local server still starts normally after this before moving on.

Step 5Verify it

  1. Back in Render, open the web service, check the Logs tab. It should say something like MMM backend listening on http://localhost:<port> with no crash after it.
  2. Copy the public URL Render shows at the top of the service page (looks like https://mmm-backend-dev.onrender.com).
  3. In a browser, or Postman, request <that URL>/api/v1/health. Expect {"status":"ok","database":"connected",...}.
  4. Request <that URL>/api/v1/auth/me with no token, expect 401, proof real login is actually being enforced, not skipped.
  5. In Postman, use the same Get New Access Token flow as TC-04, pointed at this service's URL instead of localhost:3000. Expect 200 with real name and email back.
Don't mark anything Passing yet

This isn't a new row in Backend/dev-log/for-anas/test-cases.html on its own, it's the same routes, reachable from a new address. It only really counts once Section 6 below is done and the deployed frontend is calling this deployed backend for real.

Once Step 5 is confirmed, tell the team

Share the Render URL in whatever channel the team uses. Nobody else needs Farhan's or Anas's permission to start pointing their own work at it, that's the entire point of it being shared.

06Connecting frontend to backend

The actual wiring: how the deployed frontend starts talking to the real deployed backend instead of its built-in mock data.

Already fixed, nothing to do here

The backend's API now lives under /api/v1 (e.g. /api/v1/projects), matching what the frontend's code already expected. Found and fixed 2026-08-06, see PLATFORM.md for the detail. CORS is also already wide open on the backend, no action needed for a first connection.

The one real gap, frontend side (Amna)

The frontend has a mock/real switch already built in (src/environments/environment.ts), but a production build today doesn't yet swap in a different config, so it would still use localhost and mock data no matter where it's deployed. Two files fix this:

  1. Add src/environments/environment.prod.ts:
Type this, into a new file 
export const environment = {
  production: true,
  useMockApi: false,
  apiBaseUrl: 'https://REPLACE-WITH-YOUR-REAL-RENDER-URL/api/v1',
};
  1. In angular.json, find the production configuration under architect.build.configurations, and add a fileReplacements entry so the production build actually uses the new file:
Type this, inside the existing "production" block 
"fileReplacements": [
  {
    "replace": "src/environments/environment.ts",
    "with": "src/environments/environment.prod.ts"
  }
]
  1. Commit, push, Vercel redeploys automatically. Reload the Vercel URL and the app should now be calling the real Render backend.
Real login is a separate, later step

For this first connection, leave the Render backend's AUTH_DEV_BYPASS=true, that proves the wiring works with one less moving part. Real Microsoft sign-in on the frontend needs @azure/msal-angular wired up, and a new Redirect URI added to the Entra app registration for the frontend's real URL (Anas's action item, he registered the app). See PLATFORM.md Section 3 for the full detail.

07Testing the connected app

Once frontend and backend are actually talking to each other, this defines how the team verifies a feature actually works end to end, not just that it appears to work.

Test against the shared environments, not your own laptop

Point testing at the shared Vercel URL and the shared Render backend, not a mix of one person's local frontend and another person's local backend. That combination requires matching network access and correct configuration on both sides at the same time, which is exactly what the shared environments are designed to avoid.

The backend already has a real test suite, reuse the pattern

Backend/dev-log/for-anas/test-cases.html is the backend's real, reusable test suite, ten cases, each with exact steps and an expected result, a case only counts as Passing once a real person has actually run it and it worked. The same shape works for the frontend: a similar file Amna keeps updated for her own features, for example confirming that creating a project through the real UI actually produces a row in Postgres, not just that the page renders without error.

A real end-to-end check, once Section 6 is done

  1. Open the Vercel URL.
  2. Do something that should hit the real backend, create a project through the actual UI.
  3. In pgAdmin, Query Tool against mmm_dev (or the equivalent on the Render Postgres), confirm the row actually exists.
  4. That's a real, end-to-end confirmed feature, not two halves that were only ever tested separately.
